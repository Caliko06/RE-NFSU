## 4. Top 5 ways the plan fails
1. Safari's WGSL compiler or WebGPU limits reject generated shaders (UNK, no run ever). Mitigation: run Safari FIRST, before any other work; if the fix is large, say so at hour 1.
2. "0 frames >33 ms for 3 min" is a tail metric: GC, scheduler, thermal, other apps decide it; it was never measured headed or for 3 min (best known: 3 per minute headless). Without a defined tolerance the perf block never closes. Fix the metric: vsync rows, count per minute, accept <=1/min.
3. LAN trust and speed: CA install friction on the other Mac/iPad, and HTTP/1.0 + TLS handshake per request hurting stream reads over Wi-Fi (INF until measured). A hitch-free race over Wi-Fi may need a pre-download of the track set (game/ is 1.3 GB) rather than on-demand XHR.
4. Touch with a digital steering model feels as bad as the keyboard; the OWNER's "late response" complaint returns on iPad. Needs the analog path (game's STEER_ANALOG event 0x88, host/input.c:549) or the ?steer=pad model in touch mode.
5. Parallel lanes collide: patches.py, index.html, gpu.js, d3d9.c are single files; shared build/ (8.6 GB, one build at a time, full 336 s) serialises 3 windows. Mitigate: split patches into modules, one builder window per block, Becarios never build.
Also noted: the 11-05 audit's two perf items (C18 uniforms, C19 calloc) were labelled "low severity, cost not measured": that is not evidence they are small. The audit did not cover Safari, input, LAN or iOS at all.
