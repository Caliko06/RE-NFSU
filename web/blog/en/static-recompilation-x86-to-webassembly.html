Static recompilation: turning a 2003 x86 .exe into WebAssembly

There is no source code for Need for Speed Underground. There is one Windows program, Speed.exe, and a tool that rewrites it, function by function, into code a browser can run.

Updated November 17, 2026

Emulate or translate?

An emulator reads each x86 instruction while you play and imitates it. That costs time on every frame, forever. Static recompilation pays once: before the page exists, a tool reads the whole program and writes the same logic in another language. When you open the site, the translation is already done.

The lifter

The lifter is a Python program (tools/recomp/lift.py). It opens the executable with pefile, disassembles it with Capstone and writes every guest function as one C function:

  • The eight x86 registers and the flags become C local variables, written back to a shared context only at calls and exits, so the C compiler can optimize them like normal code.
  • A direct call becomes a direct C call. An indirect call or jump, through a pointer the game computes, goes through one lookup table from guest address to function.
  • An instruction the lifter does not know becomes a TRAP: if it ever runs, the game stops and prints its address. Nothing is guessed.

The list of functions comes from a census of the executable. Today the lifter writes 13,760 of them into 160 chunks of C, and clang (for a native test build) or emcc (Emscripten, for the browser) compiles them with -O2.

Code that hides in the data

Not all of the game's code lives in Speed.exe. Its sound engine loads small x86 modules out of the .abk sound banks at run time and relocates them in memory. A static translator never sees that code in the executable, so a second pass reads all 106 sound banks, finds 79 code modules (28 distinct functions) and lifts them ahead of time. At run time the host recognizes a live copy by its header and calls the lifted version.

Proving it, bit for bit

A translation is only useful if it is exact. difftest.py runs each lifted function next to Unicorn, a reference x86 CPU, on random inputs. Both stop at the first Windows call or at the return, and every register, the x87 floating point stack and all of memory are compared. In the last full run, 5,802 of the 5,805 functions it could reach matched on every case (32,131 matching cases); the three that differ are listed by address. Unicorn is only a test oracle: it never ships in the game.

The first day of the project already ended with 1,403 functions matching Unicorn, and the same day the recompiled program started in Chrome and asked for Direct3D.

Changing the game without editing the game

Fixes and options are patches applied while lifting: small files such as patches_render.py or patches_input.py, one line per patch, each with the address it changes and the reason. The original bytes stay in the executable, and the Original 2003 version runs as shipped.
